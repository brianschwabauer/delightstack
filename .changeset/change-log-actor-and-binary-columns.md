Add a per-table change log with operation-level undo, actor attribution on every write, binary/file column types, and a file deletion queue.

**Change log / history.** Opt a table in with `Database.table(name, fn, { history: true, history_retention_days })`. Every `create`/`update`/`delete` on that table appends a row to a shared `_change_log` table: a create records the full entity as `patch`, an update records only the fields whose value actually changed plus their previous values, and a delete records the full entity as `previous`. `updated_at` is excluded from update diffs and a no-op update writes nothing, so the log only ever contains changes someone made. Rows are written inside the entity's write transaction, so a rolled-back write leaves no history behind. Read it with `db.history(table, id, { limit, before })` (newest first) and `db.changesSince(timestamp, { limit, table })` (oldest first); undo one change with `db.revert(change_id)`, which deletes a create, restores the previous values of an update, and recreates a delete with its original id and `created_at` — recording its own change entry as it goes. Retention defaults to 365 days (`0` keeps forever) and is swept in bounded batches on the Durable Object's alarm. A database where no table opts in never creates the table, and the read APIs throw a `DelightError` with code `history_disabled`.

**Operations — grouped undo.** Row-level undo is rarely what anyone wants: "undo that import", "undo that bulk retag", "undo what the agent just did" are operations spanning thousands of rows, and nothing else in the log can reconstruct which rows belonged together (timestamps and actor both group too much). Every write now also takes an optional `{ operation }` id, recorded in a new nullable `operation_id` column on `_change_log` (with an `(operation_id, created_at)` index) and threaded exactly like `actor` — so a bare-`db` write inside a scoped `batch()` inherits it, and `db.operation_id` reports the running one. Read one with `db.operationChanges(id)` (oldest first — an operation is read as a story) and undo it with `db.revertOperation(id)`, which returns how many changes it reverted. Three things distinguish `revertOperation` from a `revert()` loop: it walks the operation **newest-first** (an operation that creates a row then updates it must undo the update before the create, or the update's revert hits a row that no longer exists); the whole walk runs inside `batch()`, so one failure rolls back every revert in the run rather than leaving a half-undone import; and the reverts are themselves recorded under a **new** operation id, so the undo is revertible as a unit — pass `{ operation }` to choose that id, since the return value is a count. An unknown or blank operation id throws `operation_not_found` (404); more than 5,000 changes throws `operation_too_large` (413), because the atomicity comes from one Durable Object transaction and that has a CPU budget. `changesSince()` gains a matching `operation` narrowing alongside `table`, and `scoped(db, actor, operation)` takes it as a third argument.

**Actor attribution.** `create`, `update`, `delete`, `transaction`, `batch` and `revert` all take an optional trailing `{ actor }`, recorded on every change-log row the write produces. `scoped(db, actor, operation?)` (exported from `@delightstack/database/worker`) returns a handle that applies one actor (and optionally one operation id) to a run of writes, including writes made through the bare `db` inside its `batch()`. An unset, empty or whitespace-only actor becomes `DEFAULT_ACTOR` — `'system'`. `scoped()` is a free function rather than a `db.as()` method: a method returning `ScopedDatabase<Config>` would make `DatabaseServer` invariant in its config type parameter, breaking any consumer that widens or narrows one. Note that the actor does not yet reach `createDatabaseHandle()`'s lifecycle hooks, and `DatabaseClient` has no actor of its own. Each field of a write scope inherits independently, so passing `{ operation }` alone inside a `scoped()` run keeps the surrounding actor rather than silently re-attributing the write to `'system'`.

**Binary column types.** `schema.blob({ max_bytes })` stores raw bytes in a SQLite `BLOB` column, validated on every write and rejected with a `DelightError` when oversized; blobs are never tokenized, never in the search index, and never in a `sync()` payload. `schema.file({ store })` stores a `{ key, size, mime, sha256?, name? }` descriptor of an object living in an external store, with `resolveFile(reference, store)` to read the bytes back — structurally typed against `{ get(key) }`, so an R2 bucket, an S3 wrapper or a directory shim all satisfy it. `transaction()`'s create op also gains `preserve_id`, which keeps the id and `created_at` from the supplied data instead of generating fresh ones — the primitive behind reverting a delete, and useful for imports and restores. Inserting onto an id that is still live throws a `DelightError` (`entity_exists`, 409) rather than a raw SQLite constraint error.

**A third field tier: carried, not indexed.** `.searchable()` has always meant both "sync this to the client" and "index it"; there was no way to ask for one without the other. `.carried()` now marks a field as synced but never tokenized — it gets no entry in `index_schema`, joins neither `searchable_fields` nor `sortable_fields`, and is rejected in `where`, `order` and a search's `fields` list, as a compile error in a typed schema and a `DelightError` (`carried_field_not_queryable`) at runtime. Use it for anything a client renders but nobody searches: a rendered HTML body, a layout config, a media descriptor. Be aware of what the tier costs: a carried field ships to every client on every change to the row and is stored in each one's IndexedDB, so a multi-megabyte carried value bloats both the sync payload and the client cache in proportion. It is available on every field type except `blob()`, and is mutually exclusive with `.searchable()`/`.sortable()`. A `schema.file()` reference is carried by default, since its purpose is to let a client build a URL; pass `carried: false` for a reference that should stay server-side.

**Blob columns and `revert()`.** Blob bytes are never recorded — `JSON.stringify` of a `Uint8Array` costs roughly five bytes per byte, which would make the log larger than the table and exceed the Durable Object's 2MB per-value limit. Instead each omitted column is recorded as a `{ __blob_omitted: true }` marker, so `revert()` can tell "bytes we did not keep" from "column was empty". Reverting a change that would drop blob data throws a `DelightError` (`blob_not_recoverable`, 409) naming the columns rather than restoring a quietly incomplete row; pass `{ without_blobs: true }` to restore everything else and leave them unset, which still fails when the column is required.

**File deletion queue.** Deleting a row deletes its reference, not its object, and the application cannot clean up the orphan unaided: by the time it sees the row is gone, the key went with it. The database is the only component that knows both when a row died and what key it held, inside the write transaction — so it now records that. A `_file_gc` table is bootstrapped (like `_change_log`, only when at least one table actually has a `file()` column) and a row is enqueued when a row holding a reference is **deleted**, or an **update** replaces a reference with one whose `key` differs. Nothing is enqueued on create, on an update that changes only `mime`/`name`/`metadata` (same object, better description), or on one that changes only `store` (a migration record, not an orphaning). The `store` recorded is the reference's own if it has one, else the field's default. Drain it with `db.pendingFileDeletions({ limit })` (oldest first, default 100, max 1000) and `db.releaseFileDeletion(id)` / `db.releaseFileDeletions(ids)` — delete first, release second, so a crash re-delivers rather than losing the key. Reference counting is deliberately **not** implemented and no `LIKE`-based scan ships: references live in the internal `json` overflow column, so finding other holders of a key would mean scanning every row of every table with a file column — expensive on storage billed per row read, and wrong besides (`LIKE '%key%'` matches keys that merely contain each other). The queue therefore reports *intent, not safety*: an application that content-addresses its keys MUST check for remaining references itself before deleting.

**Per-row `store` and open `metadata` on `FileReference`.** `store` was schema-level only, which pinned every row in a column to one bucket forever and blocked bucket migrations, hot/cold tiering and per-tenant buckets. A reference may now carry its own `store`, so the effective store is `reference.store ?? field default`; `file_fields[name].store` is documented as the default, and `resolveFile()` keeps its signature but tells the reader to pick the binding from the effective store. A reference may also carry `metadata: Record<string, string>` — the escape hatch for app-specific bits (page count, duration, EXIF date, encoding) that stops the descriptor growing a new optional field per application. Values are strings only, rejecting nested objects, arrays, numbers and `null` with a message naming the key, mirroring how S3/R2 object metadata works. It lives on the reference rather than in sibling columns because it then moves **atomically** with the file: replacing the object replaces its description in one write, so there is no window in which the row claims a 12-page PDF while `key` already points at the 40-page one.
