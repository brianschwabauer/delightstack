The **client** half: `@delightstack/crdt/client` now exists alongside `/server`, and the `exports` map lists it. `CrdtClient` owns a set of open Loro documents, their local persistence and the conversation with the document servers; it owns neither the connection nor the schema.

**The bootstrap gate, which is the reason most of this is shaped the way it is.** A Loro shallow snapshot imports only into a document whose version already covers the snapshot's shallow start — an *empty* document being the special case that always works. A rich-text editor's very first transaction writes an empty document into the CRDT, and that single operation is enough: after it, a compacted server can never bootstrap the device. `import()` returns `{ success: {}, pending: {} }`, throws nothing, and leaves the document untouched, so both sides believe they are fine while the device stops syncing forever. `open()` therefore returns a handle that is `loading`, cleared on the first of the server's `sync`, local storage already holding operations, or `bootstrap_timeout_ms` (default 1.5s, so a genuinely offline first run still works) — and `transact()` **throws `bootstrap_pending`** until then. The rule was already written down and it was not enough; the gate has teeth. `await handle.ready()` before mounting an editor.

**Transport is injected, mirroring how the server kept it out via `syncFor()`.** `CrdtTransport` is `connected` / `send` / `onMessage` / `onConnectionChange`, and messages are structured objects carrying `Uint8Array` payloads rather than frames, so framing stays a wire decision. The message set maps one-to-one onto the server: `subscribe` → `syncFor()`, `update` → `applyUpdate()`. In a real app one connection already carries metadata sync and presence, so a CRDT package that opened its own would be a second socket, a second reconnect policy and a second auth handshake — and an interface is a transport a test can partition mid-edit. Re-subscribing on reconnect *is* the catch-up protocol (the server answers with a version-vector diff, which covers an offline session of any length), so a transport that reconnects without firing `onConnectionChange` leaves documents stuck.

**Durability.** `transact()` is synchronous and appends the update blob to the local pending log before returning; persistence completing and the network send are fire-and-forget. That is only enforceable with `createSyncAccessHandle()`, which is worker-only — run this layer in a SharedWorker. `OpfsCrdtStorage` still works on the main thread through `createWritable()`, where the write is merely *queued* synchronously, and reports which you got as `.durable`. On disk each document is a snapshot plus an append-only log of framed records (updates and ack tombstones), folded every `snapshot_every` records; a truncated tail from a crash mid-append is dropped rather than failing the open. Remote blobs are logged too, since the snapshot is only rewritten periodically. Unacked local blobs are re-appended *after* a fold even though the snapshot already contains their operations — the snapshot preserves the content but only a log record preserves the `op_id`, and without it a reload loses the ability to resend.

**Sending.** Debounced by `send_debounce_ms` (default 200ms), with a run of never-sent commits coalesced into one update by re-exporting from the first one's version vector; the spike measured ~90 bytes of CRDT inside a ~175 byte frame per keystroke, so roughly half the traffic was framing. Blobs already on the wire are never re-coalesced — that would re-mint their `op_id` and defeat the server's deduplication — so a reconnect resends them unchanged, in order. Nothing is sent before the connection's `subscribe` has been answered, because the answer is where `reset` lives.

**Eviction and quota are two different things.** A document stays resident `idle_evict_ms` (default 5 minutes) after its last reader, then is snapshotted and dropped from memory; `open()` restores it. A document holding unacked commits is not evicted, since dropping it leaves nothing in memory to resend from. Separately, `quota_bytes` (default 2GB) is a soft cap on local body storage swept LRU by whole document — never a resident document, and **never one holding unacked local commits**, so quota pressure can never be a route to losing an edit the server has not seen.

**`reset` is surfaced, never applied.** When the server says this device predates the retained history, the client marks the handle unusable (`transact()` throws `reset_required`), sets `sync_state` to `error`, and calls `on_reset({ node_id, unacked_ops })`. Discarding a user's offline work is a decision a UI makes; `purge(node_id)` then `open(node_id)` is the recovery path.

`sync_state` (`synced` / `syncing` / `offline` / `error`) and `pending_count` are Svelte 5 runes, so `svelte` is now an **optional** peer dependency. `storage: 'idb'` throws `not_implemented` on purpose: IndexedDB cannot offer the synchronous append `transact()` promises, so an IndexedDB backend would quietly weaken the contract rather than widen support. `MemoryCrdtStorage` is exported for tests and for environments with no durable storage at all.

**Tests.** The client suite drives `CrdtClient` against the real `CrdtDocumentServer` over real SQLite through a loopback transport, including a test that first *demonstrates* the empty-doc-then-compacted-server trap against the real server and then shows the gate preventing it. OPFS does not exist in Node and no DOM shim implements it, so storage is exercised through `MemoryCrdtStorage` — the same interface storing the same framed bytes, which keeps framing, tombstones, reload replay, snapshot folding and the quota sweep real. Not covered, deliberately: that `createSyncAccessHandle().write()` really is synchronous in a browser, the main-thread positional-append path, two-worker handle contention, and browser-initiated eviction.
