Fix two ways the reactive list handle could go permanently stale or empty.

**Zombie handle after a template-branch swap.** `db.list()`'s handle created its `$effect.root()` from inside `createSubscriber`'s start callback, which Svelte runs inside a render effect owned by whichever effect FIRST read the handle — typically a transient `{#if}`/`{#key}` branch in the consuming component. Svelte parented the root to that branch. If a dependency of the handle's reactive query changed (clearing the root's CLEAN flag as `Batch.schedule()` climbed the parent chain) in the same window that the branch was destroyed, the root was spared by orphaning (`parent = null`) while the queued traversal still started from the old ancestor — so nothing ever restored the flag. Every later schedule then hit the non-CLEAN root and took the "already dirty, bail" early exit: the reactive-query effect and the query watcher never ran again, no error was thrown, and `#stop` never fired because the replacement branch kept the subscriber count above zero. The handle served the same stale results forever. The start is now deferred to a microtask, so `$effect.root()` is created with no active effect and the root is parentless from birth — nothing can orphan it mid-schedule. A start-cycle token keeps start/stop paired: a subscribe immediately followed by an unsubscribe cancels the pending start rather than reviving a torn-down handle. `db.get()`'s `EntityHandle` had the identical exposure (its version-watch effect lived in a root born the same way) and gets the same deferral; its `live` getter counts the pending-start window so the client's cache eviction still never drops a subscribed handle.

**Queries racing the client's `init()`.** The worker proxy exists as soon as the worker module loads, which is well before `init()` has registered the tables with it, so a query that landed in that window was rejected with `Unknown entity type` — the handle caught it, went to `status: 'error'`, and rendered an empty list at boot with nothing to retry it. `init()` now exposes its promise to the handles, and the subscribe, push and one-shot query paths — `db.get()`'s fetch path included — await it before touching the worker. There is nothing to await when `init()` was never called (SSR, or a fetch-only client), so the `/api/<entity>` fetch path is unaffected and cannot deadlock; a failed `init()` also lets the query through, so the real error surfaces instead of a hang.
