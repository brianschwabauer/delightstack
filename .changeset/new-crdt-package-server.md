New package: collaborative document storage for Cloudflare Durable Objects, built on Loro. This changeset covers the **server** half; the client and ProseMirror entries are declared but not yet implemented.

**`CrdtDocumentServer`.** One Durable Object per document, holding one Loro document plus the append-only log that produced it, and everything derived from that pair. `applyUpdate(op_id, actor, blob)` dedupes on a client-generated `op_id` — every mutation in a local-first system crosses at least one retry boundary, so a repeat is normal traffic: it returns `applied: false` with the current frontier and the original `seq`, and appends nothing, so the *log* does not grow on retries even though Loro's `import` is idempotent anyway. `listUpdates()` and `listSessions()` are derived from stored metadata (`frontier` after applying, `byte_size`) and never decode an update blob, which is what makes opening the history rail on every document affordable; sessions — same actor, gap under `session_gap_ms`, no checkpoint between — are computed at read time and never stored, so the grouping gap stays a UI tuning knob rather than a migration. `checkpoint()`, `restore()`, `getVersion()`, `snapshot()`, `compact()` and `runProjection()` complete the surface.

**Entry points are pinned per environment, deliberately.** Loro ships several wasm builds behind one specifier and export-condition resolution picks a broken one in two of the three environments that matter: in workerd the `browser` build throws at module scope (the Worker never boots), and under Vite the `bundler` build is refused outright. `@delightstack/crdt/server` names `loro-crdt/bundler` and `@delightstack/crdt/client` names `loro-crdt/web` (streaming compile — the `browser` build fetches 3.2MB with a **synchronous XHR** and decodes it byte by byte on the main thread), while the root entry is types only and pulls in no wasm at all. Server code imports Loro from `src/loro.server.ts` and never from the bare specifier, so there is exactly one place to get this wrong.

**Three methods are async, against the original design sketch.** Snapshots above `inline_snapshot_max_bytes` (512KB default) are tiered to R2, and R2 is async, so `getVersion`, `snapshot` and `compact` return promises; a synchronous `getVersion` could only ever read inline snapshots and would silently cap the document size at which history works. Everything on the hot path stays synchronous, because DO SQLite and Loro both are.

**Compaction, and the three Loro behaviours it is built around.** `export({ mode: 'shallow-snapshot', frontiers: F })` does **not** export the state at `F` — `F` is where retained history *starts*, and the exported state is always the document's current state, so a snapshot "at a checkpoint" has to come from a throwaway document replayed to that checkpoint first. `forkAt()` is not implemented on shallow documents, so time travel is replay-then-export rather than fork; and because exporting a `checkout()`-ed document exports its whole oplog state rather than the checked-out state, the throwaway document's log must *end* at the target. A version whose blobs were discarded and which is not a checkpoint throws `frontier_unreachable` (410) rather than being approximated with the nearest snapshot. Every checkpoint at or before the boundary gets a pinned snapshot at its exact frontier before a single blob is deleted, and steps 2–4 run in one `transactionSync`.

**Compaction can decline, and that is the invariant rather than a failure.** Checkpoint snapshots are mandatory and cost more than the op blobs they replace on small or checkpoint-dense documents — a 9-op document was measured growing 871B → 1188B, and the package's own 10,000-edit/50-checkpoint test is another case where the snapshots outweigh the whole log. So the transaction measures its own result and rolls itself back with `skipped_reason: 'would_not_shrink'` rather than letting "compaction never increases stored bytes" be false. `below_threshold`, `retention_forever`, `nothing_to_do` and `peer_floor` are the other reasons; `{ force: true }` overrides all of them for an explicit user action.

**The peer floor.** Once history is trimmed to a shallow start, a peer whose version predates that start is unrecoverable in *both* directions: it cannot be caught up (a shallow snapshot imported into a document behind its shallow start returns success and changes nothing) and its own operations can never be accepted, because their dependencies are gone on the server too. Nothing throws — the device just stops syncing forever while both sides believe they are fine. So `compact()` never trims past `min(acked_seq)` over peers seen within `peer_floor_ttl_ms` (30 days). Peers are registered by `syncFor()`, which also makes the incremental-vs-bootstrap decision that cannot be delegated (`shallowSinceVV().compare(peer_version)` — an `export({ mode: 'update', from })` on a shallow document returns a blob whose dependencies were trimmed and the receiver reports success anyway), or explicitly via `notePeer()`/`forgetPeer()`. A device that reappears past the TTL is told `kind: 'reset'`, which is data-losing and must be surfaced, not performed quietly. A document with no registered peers has no floor — correct for a server-authoritative deployment, wrong for one with real offline devices.

**Tests.** A seeded convergence harness — 2–5 peers from a common base, randomized edit scripts (insert, delete, replace, split, join, move, format, image, same-offset typing), random partition and reconnect, delivery in random order with duplicates, then every peer asserted byte-identical on content, markdown projection, block ids and version vector. 50 scenarios in CI, `CRDT_SCENARIOS=500` for nightly; failing seeds are checked in as regression cases. Plus the known-hard cases and one test per history invariant, including the real version of "every checkpoint stays checkoutable forever": 10,000 edits, 50 checkpoints, compaction run to completion, all 50 checked out and compared byte for byte. The Durable Object harness runs the real class against real SQLite through `node:sqlite`, because a mock that records SQL strings can only prove the statements were issued, not that they were right.
